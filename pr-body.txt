## Summary

Phase 2 of the concurrent-batch TUI visibility feature (see #516).

**Phase 1** (already shipped): after a parallel wave completes, each tool row in scrollback gets a `∥i/N` badge showing which wave it ran in.

**Phase 2** (this PR): during the window when tools are *still in-flight*, the overlay shows a `[×N]` pending badge next to each spinner, so the operator can see parallel execution *as it happens* — before any result arrives.

## How it works

1. **Emit a `tool.batch.start` event**: `executeBatch`'s inner `runConcurrentBatch` calls a new `batchEventSink` callback at the top of each concurrent wave (width ≥ 2), before any handler fires. The dispatcher accumulates these into `pendingBatchEvents[]`. The provider generator drains and yields them as `tool.batch.start` ProviderEvents right after `executeBatch` returns, which get translated to `batch-start` OutputEvents by the stream consumer.

2. **Live overlay consumes `batch-start`**: `handleOrchestratorEvent` handles the new `batch-start` OutputEvent by calling `toolLane.notifyBatchStart(batchSize, toolUseIds)`, then triggers a repaint.

3. **Badge appears on in-flight rows**: `getOverlay`'s in-flight row renderer appends `pendingBatchBadge(entry.toolUseId, this.pendingBatch)`, which returns `[×N]` (dim) for member ids.

4. **Badge clears automatically**: `addResult` checks after each result whether all batch member ids have resolved, and nulls `pendingBatch` when the wave is fully done.

## Constraints preserved

- **Append-only scrollback**: badge only touches the live overlay (getOverlay), never the flush/scrollback path.
- **No behavior changes**: batching/concurrency behavior and `concurrencySafe` flags are untouched.
- **Phase 1 backward compat**: `∥i/N` completed badges continue to work via the existing `batchBadge()` path.
- **Sequential batches** (bash, edit_file, …): never emit `batch-start` — only `isConcurrencySafe` waves with ≥ 2 calls.
