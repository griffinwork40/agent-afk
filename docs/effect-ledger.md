# External effect ledger

The existing ledger at `src/agent/effect-ledger/` fsyncs a `pending` intent before dispatch of a classified external action. The post hook updates that same id. `executed` means a response was observed, not that a remote effect was independently verified. `confirmed` records independent reconciliation via `EffectStore.reconcile(id, readRemote)`. `failed` means definitive non-application, such as a pre-send rejection or HTTP 4xx. `unknown` means dispatch occurred but the result was lost or an error result cannot prove non-application. A `pending` intent left by a crashed process is treated as unknown on resume. The historical `ambiguous` status is a legacy duplicate note, not the outcome-unknown status.

A deterministic key covers operation type and canonical raw arguments. For the same key and session, the first retry after `unknown` or abandoned `pending` is blocked with instructions to verify remote state; its acknowledgment is persisted on the original record. Re-issuing the same call after verification proceeds as a new intent linked through `retryOf`. This acknowledgment records that the warning was delivered, not proof that verification happened. A prior `executed` or `confirmed` attempt produces a warning but does not block intentional repeats. Different arguments or sessions are independent. Ledger read/write failures fail open, so this is a safety aid rather than exactly-once delivery. Concurrent in-flight identical calls are blocked in one process. Remote verification itself remains the caller's responsibility.

HTTP POST, PATCH, PUT and DELETE are classified as external. Mutating HTTP methods are never automatically retried inside the HTTP client: each new tool invocation must pass the pre-execution gate. Existing read-only HTTP retries remain unchanged.

For an API that **documents `Idempotency-Key` support**, set `web_request.remote_idempotency: true`. The pre-hook merges a remote key into headers without changing other headers or overwriting an existing key (case-insensitive). There is no automatic host allowlist: support varies by endpoint and must be checked by the caller. The remote key is persisted before dispatch and reused only for retries of an uncertain attempt, including after restart. It is distinct from the deterministic ledger lookup hash: independent sessions and intentional repeats get fresh remote keys so valid repeated actions are not silently suppressed. Explicit caller keys remain caller-owned. Reads and requests without opt-in are unchanged. Ledger failures still fail open, so remote deduplication is not guaranteed.

`EffectStore.reconcile(id, readRemote)` encapsulates unknown-to-confirmed reconciliation. The trusted adapter receives a detached record and must perform only a read, matching the exact remote resource/operation identity (for a PR: repository and head, not just title). Return `{ matched: true, evidence: { ...resourceIdentity } }` only on a positive match. Evidence is redacted and persisted with `reconciledAt`; unmatched, missing-evidence, and throwing reads leave the record uncertain. Unacknowledged `pending` intents are not probed (they may still be in flight); after a crash, the caller must establish abandonment and call `acknowledgeRetry(id)` before reconciling that pending record. The helper re-reads local status before writing and skips settlements observed then. This append-only store has no cross-process compare-and-swap: callers must serialize reconciliation with other writers to that record; it is not a transactional distributed ledger. It never dispatches/retries the original action. No general-purpose automatic reconciler or model-facing reconciliation tool is provided: operation-specific read adapters remain caller-owned.
