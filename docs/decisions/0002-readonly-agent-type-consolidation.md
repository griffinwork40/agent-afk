# ADR 0002 — Read-only agent types: keep the capability, collapse the split

Status: **Partially accepted.** The headline proposal — collapsing the two
read-only agent types into one — is **still Proposed and awaiting a maintainer
decision**; it has not been implemented. Decision item 3 (the shadow-warning)
has landed. Decision items formerly numbered 4-first ("fix trace attribution")
and 4-second ("add a wall-clock bound") are both **void**: each was generated by
a measurement error, retracted in F6 and F8 respectively.

Branch: `afk/remove-redundant-agents`.

---

## Context

The question raised was whether the two vendored named sub-agent types —
[`research-agent`](../../src/skills/_agents/research-agent.ts) and
[`git-investigator`](../../src/skills/_agents/git-investigator.ts) — are
"truly optimal / necessary", or whether they should be **removed** and the
bundled skills that dispatch them rewritten. The stated suspicion was that
they cause "a lot of bugs and friction" and are "used for the wrong things".

This ADR records the investigation, two reversals of its own conclusion, and
the resulting recommendation. It is written down because the conclusion
reversed twice and is not re-derivable cheaply.

## Method

Four parallel investigation lanes (mechanics / consumer map / production-trace
friction / git history), then a `devils-advocate` critique wave, then a
pre-registered falsifying experiment. Provenance is labelled per finding
because the confidence differs sharply between them.

## Findings

### F1 — The read-only lock is mechanically real (verified directly)

Two enforcement layers, not prose:

- [`dispatcher.ts`](../../src/agent/tools/dispatcher.ts) `toolDefs` getter
  filters the **advertised** tool schemas by `permissions.allowedTools`, so a
  locked child never sees `bash` / `write_file` at all.
- [`permissions.ts:20-36`](../../src/agent/tools/permissions.ts) rejects any
  disallowed call at execution time.

Corroborated live: a `research-agent` dispatched during this investigation was
mechanically refused when it attempted to dispatch `Explore`.

### F2 — Deletion would hard-break ~10 dispatch sites (verified directly)

An unresolved `agent_type` is a **hard error**, not a fallback to generic —
[`subagent-executor.ts:430-431`](../../src/agent/tools/subagent-executor.ts).
Ten bundled `SKILL.md` waves dispatch `research-agent` by bare name (review,
shadow-verify, devils-advocate, simplify, ship, research, refactor Wave 1,
diagnose) plus [`audit-fit`](../../src/skills/audit-fit/index.ts), which builds
its own gate from `researchAgent.allowedTools`.

### F3 — Production failures are infra, not agent defects (delegated; attribution-limited)

Full-corpus scan of 12,292 witness traces, 1,250 dispatches since 2026-07-14:
all 88 failures were rate-limit (37), stream-cutoff (33), or timeout (13).
**Zero** unknown-agent-type, no-such-tool, or max-turns errors. `git-investigator`
succeeded 87.8%. Zero misuse-shaped prompts found. **Confidence: medium** —
see F6; the scan's own attribution basis is unreliable.

### F4 — The normalizer duplication is deliberate, and there are three copies (verified directly)

[`resolve.ts:39-42`](../../src/agent/agents/resolve.ts) carries an explicit
`// Invariant:` comment: the `KNOWN_AFK_TOOL_NAMES` set is *"Duplicated (5 lines)
rather than imported to keep the layering direction src/agent → src/skills
one-way-free."* A third copy exists at
[`tool-injector.ts:388-392`](../../src/agent/plugins/tool-injector.ts).

Consequence: "collapse the two duplicate normalizers" — proposed early in this
investigation — would have **violated a documented Invariant**. Retracted.

### F5 — The read-only binding is not tamper-evident (verified directly)

[`registry.ts:5-11,26-27`](../../src/agent/agents/registry.ts): builtins sit at
the **bottom** of the precedence order, and a duplicate name across scopes
*"shadows silently by design"*. A single file at `~/.afk/agents/research-agent.md`
declaring `tools: Bash, Write` silently converts every "mechanically locked
read-only verifier" in all ten consumer skills into a write-capable agent,
machine-wide, with no warning and no trace event. Currently un-shadowed on this
machine (checked: no user- or project-scope `agents/` directory exists).

The adjacent MCP escalation path is **contained**: `nesting.ts` and
`child-config.ts` carry zero `mcpManager` references, so `withMcpToolsAllowed`
cannot widen a restricted child's allowlist — matching the containment claim
documented at `permissions.ts:77-81`.

### F6 — RETRACTED: trace attribution works (the instrument was broken, not the code)

An earlier revision of this ADR claimed tool-call attribution was broken,
citing "0 of 2,281 `tool_call` rows carry a `subagentId`" and "1,026 `bash`
calls credited to a parent that made ~15". **Both numbers were a query error.**

`subagentId` lives at `.payload.subagentId`, not at the event top level.
[`subagent.ts:823`](../../src/agent/subagent.ts) sets it on every forked child
(placed after the `...options.config` spread specifically so a caller cannot
override it), and the shared builders in
[`tool-call-trace.ts`](../../src/agent/providers/shared/tool-call-trace.ts)
stamp it onto both `started` and `completed` payloads. Querying `.subagentId`
matches nothing, which silently collapses every child's calls into the default
"parent" bucket.

Correct query:

```
jq 'select(.kind=="tool_call") | select(.payload.subagentId != null)
    | [.payload.subagentId, .payload.name]' trace.jsonl
```

Attribution is complete and per-child, as F7 now demonstrates. **The
"fix attribution" work item this finding generated is void — there is nothing
to fix.**

Retained lesson: a measurement reporting a suspiciously *total* result (0 of
2,281; 100% of calls credited to the wrong actor) is far likelier to be a
broken instrument than a broken system. Verify the instrument before reporting
the finding — and certainly before writing it to durable storage.

### F7 — Falsifying experiment: the guarded failure mode does not occur (verified directly)

Pre-registered falsifier: if stripping the lock produces no write attempts, the
lock guards a non-occurring failure mode.

Three write-capable agents were dispatched on realistic research tasks lifted
from real skill dimensions (each *tempting* shell use: `npx knip`, `vitest`,
`git log`), in an isolated worktree where writes were permitted and observable,
with budgets identical to the locked arm.

The three locked control arms were killed by an account rate limit mid-run, but
they had already executed enough tool calls to serve as a partial control (their
counts are therefore **lower bounds**).

Per-arm tool usage, from `.payload.subagentId` attribution:

| arm | bash | agent | read_file | grep | glob | write/edit |
|---|---|---|---|---|---|---|
| T1-locked | — | — | 20 | 40 | 4 | **0** |
| T1-unlocked | 2 | 2 | — | — | — | **0** |
| T2-locked | — | 4 | 6 | 10 | 2 | **0** |
| T2-unlocked | 48 | 2 | — | — | — | **0** |
| T3-locked | — | 2 | 2 | 4 | — | **0** |
| T3-unlocked | 22 | — | 6 | 2 | — | **0** |

Three results, in ascending order of importance:

1. **Zero `write_file` / `edit_file` calls by any child, locked or unlocked.**
   Three write-capable agents, on repo-inspection tasks, in a worktree where
   writes were permitted — no mutation was attempted. Corroborated
   independently by `git status` (clean). The failure mode the lock is sold on
   did not occur.
2. **The lock is not inert — it materially changes behavior.** Unlocked arms
   reached for `bash` immediately and heavily (2 / 48 / 22 calls). Locked arms
   could not, and substituted read tools: T1-locked spent **64 read-tool calls**
   (40 `grep` + 20 `read_file` + 4 `glob`) and was still unfinished, where
   T1-unlocked answered the same question in **6 calls**. A ~10× efficiency
   penalty, and a lower bound.
3. **Under the lock, agents route around it rather than doing without.** Both
   locked arms that needed git dispatched the `agent` tool (T2-locked ×4,
   T3-locked ×2) — the scoped `Agent(git-investigator)` grant firing exactly as
   designed. The nested-dispatch subsystem exists to hand back the shell the
   lock removed, and it is genuinely load-bearing *given the lock*.

Synthesis: the lock's stated benefit (mutation prevention) is unrealized,
because the mutation never occurs. Its cost is measurable — ~10× more tool
calls, or a second agent dispatch. That cost is also plausibly self-inflicting:
the locked arms' 64-call grep marathons generate more token pressure, and it was
the locked wave that hit the rate limit.

### F8 — RETRACTED: the wall-clock bound already exists (verified directly)

An earlier revision of this ADR ranked "bound dispatches on **time**, not only
iterations" as work to do, citing "a 50-iteration-capped agent died at the
45-minute wall clock, proving the iteration cap bounds the wrong axis."

The wall-clock bound is already implemented, and the cited death **is that
bound working**:

- [`subagent.ts:108`](../../src/agent/subagent.ts) — `SUBAGENT_DEFAULT_TIMEOUT_MS = 45 * 60_000`.
- [`subagent.ts:1023`](../../src/agent/subagent.ts) — applied to every fork as
  `options.config.timeoutMs ?? resolveSubagentTimeoutMs()`.
- Env-tunable via `AFK_SUBAGENT_TIMEOUT_MS`; `0` restores unbounded.
- Pinned by test: `subagent.test.ts:897` asserts the 45-minute value, and
  `:901-924` asserts a child exceeding it is killed with
  `timed out after <ms>ms`.
- Two further bounds exist on adjacent axes: an **8-minute idle** timeout
  (`subagent.ts:160`, `SUBAGENT_DEFAULT_IDLE_TIMEOUT_MS`) and a **60-minute
  background** variant (`subagent.ts:193`).

So the agent did not die *despite* a bound on the wrong axis; it died *because*
the correct-axis bound fired at exactly its configured value. The observation
was evidence the mechanism works, and it was recorded as evidence the mechanism
was missing. **That work item is void — there is nothing to add.**

This is the same error shape as F6, one step removed: F6 mistook a broken query
for a broken system; F8 mistook a working guard for an absent one. Both were
recorded confidently, and in both cases a single targeted file read at the
already-known path would have caught it. The general rule both support: before
writing "X is missing" to durable storage, grep for X.

## The reversals

Recording these because each was an error made with confidence.

**Reversal 1 — "collapse the two normalizers".** Framed as removing accidental
duplication. It was neither accidental nor two: F4. The `devils-advocate`
critics surfaced it; direct file reads confirmed it.

**Reversal 2 — "the two types must stay separate".** The original argument:
merging `git-investigator`'s read-only bash into `research-agent` would
downgrade a *hard* guarantee ("cannot shell at all") to the read-only-bash
classifier, which [`readonly-bash.ts:5-22`](../../src/agent/tools/readonly-bash.ts)
explicitly disclaims as best-effort and **not a security boundary**.

The evidence inverts this:

- the **hard lock** guards a mutation event that occurred **0 times** in 3/3
  unlocked trials (F7) and **0 times** across 735 production dispatches (F3);
- the **best-effort classifier** blocked **6 real mutating commands in a single
  session** (F6), and 255 of 268 in the #714 audit.

The mechanism called weaker is doing the actual work. The mechanism called
load-bearing guards an event that does not happen.

**Reversal 3 — two invented work items.** Both retractions above (F6, F8)
follow one pattern: a *measurement* was wrong, and the resulting work item
described fixing a mechanism that was already working. "Fix trace attribution"
came from a `jq` path error; "add a wall-clock bound" came from reading a
timeout firing at its configured value as evidence that no timeout existed.
Neither survived a single targeted read of the file already named in the claim.
Two of the four original decision items were therefore artifacts of the
instrument rather than findings about the system — which is the main reason to
distrust this document's uncited prose over its citations.

## Decision

Do **not** delete the read-only capability — F1 and F2 stand. But the two-type
split is the weakest part of the design, not the strongest.

Ordered:

1. **Collapse `research-agent` + `git-investigator` into one read-only type**
   carrying `bashReadOnly: true`. Deletes the second type, the
   `Agent(git-investigator)` scoped grant, `extractNestedAgentScope`,
   `nestedAgentAllowlist`, and the "which type do I dispatch" ambiguity across
   ten `SKILL.md` files — while keeping the guard that empirically fires
   (the read-only-bash classifier) and dropping the one that never fires
   (the total bash exclusion).

   This is now backed by direct measurement rather than inference: F7 shows the
   excluded capability is used for read-only work in 3/3 unlocked trials, the
   mutation it excludes never occurs, and the exclusion costs ~10× more tool
   calls or a second agent dispatch.

   *(A prior revision ranked "fix trace attribution" first. That item was
   generated by a measurement error and is void — see F6.)*

   **Status: NOT implemented — this is the open maintainer decision.** It is
   the only item here that changes runtime behaviour for the ten consumer
   skills, and its own evidence base has holes the Open threads section names:
   n=3 per arm, no arm finished, and the merged design's only remaining
   boundary (the read-only-bash classifier) has an unmeasured hit-rate under
   research-shaped prompts. Recommend measuring that hit-rate before merging
   the types, not after.
2. **Delete the `src/skills/_agents/` TS-wrapper layer**; construct builtins
   from the byte-pinned markdown frontmatter through the generic
   `parseAgentMarkdown` + `resolveAgentToolAccess` pipeline. Dissolves F4
   instead of violating it, and removes the dead `toAgentDefinition` fossil.
   **Status: NOT implemented** — moderate blast radius (`audit-fit` builds its
   gate from `researchAgent.allowedTools`); wants an `/impact-map` pass first.
3. **Warn when an agent file shadows a read-only builtin** (F5).
   **Status: IMPLEMENTED** — `warnIfShadowsBuiltin` in
   [`registry.ts`](../../src/agent/agents/registry.ts), wired into all three
   displacement points (`scanScope`'s file merge, the plugin merge, and the
   config-tier merge), with four tests in `registry.test.ts`. Precedence is
   deliberately unchanged: overriding a builtin stays intended operator power,
   the override just stops being silent. The warning names the specific
   restriction being discarded (tool allowlist, and the read-only bash gate
   when the displaced builtin carried `bashReadOnly`).

   Deferred from this item: the **trace event**. The warn sink is already
   threaded through `loadAgentRegistry` (`options.warn`), but no trace writer
   is, and threading one into a synchronous bootstrap-time scan is a wider
   change than the warning justifies on its own.

   *(A prior revision paired this with "add a wall-clock bound". That half is
   void — the bound already exists and the evidence cited for its absence was
   the bound firing correctly. See F8.)*

Keep the SHA-256 byte-pin: the vendored prompts are hash-identical to their
upstream plugin counterparts, so the pin is a real sync guard against silent
divergence, not a self-referential tax. (`contract.md` has no upstream
counterpart; that one pin *is* self-referential.) Per the convention already
followed by `vendored.test.ts`, the pin records hashes rather than the upstream
location.

## Open threads

- The locked control arms ran only partially (killed mid-run by a rate limit),
  so their tool counts are lower bounds and no arm produced a *finished*
  locked-vs-unlocked answer-quality comparison. The ~10× efficiency claim is
  directional, not precise.
- F7's mutation result rests on absence-of-evidence with n=3 per arm. A
  conclusive version raises n to ~10 and lets every arm run to completion.
- Not tested: whether an agent with read-only bash *attempts* a mutating
  command and gets caught by the classifier (the merged type's actual safety
  path). The 6 `bash` denials observed were git-investigator's gate firing, but
  under the merged design that gate becomes the only boundary, so its hit-rate
  under research-shaped prompts is the number that matters and is unmeasured.
- **Live contradiction:** 2 `glob` denials fired in the session above. The
  delegated friction scan claimed the Title-case/snake_case denial bug was
  "confined to 2026-07-01/02 and predates these agents". It appears to be live
  and is unexplained.

## What would falsify this decision

1. The upstream plugin stops shipping these agents → the byte-pin's upstream
   vanishes → the vendoring becomes pure tax.
2. Removing the lock entirely and running the ten bundled skills yields zero
   write attempts *and* no quality loss → the capability itself is unnecessary.
3. The maintainer stops shipping `awa-bundled` skills → all ten consumers
   evaporate → both types become dead weight.
