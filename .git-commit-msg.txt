fix(#4370): address advisory findings from #4259 auth account switch review

Addresses all seven advisory findings surfaced during review of #4259
(merged dd7410af), verified on HEAD b2a2cb48bd808d4828209590ea03b67809adc104.

## Findings addressed

### Medium (test coverage)

**Finding 1** — `compact-handler.ts:144-153`: `credential_swap` emission from
the compaction path had zero test coverage. Added
`compact-handler.credential-swap.test.ts` with four cases: swapped:true emits
the event; swapped:false does not; null (no swap needed) does not; a throw
inside syncClientWithStore does not propagate (best-effort).

**Finding 2** — `retry-layer-turn-start.test.ts:62-66`: No test for
`credentialFromStore: true` + env var set (defence-in-depth path in
`storeAheadOfClient`). Added two cases to the existing file: the env-var guard
blocks a swap even when `credentialFromStore` is explicitly true; the positive
path (true, no env var, store moved) still swaps correctly.

**Finding 3** — `compact-handler.ts:125-144`: `syncClientWithStore()` is inside
the per-retry `sessionSummarize` closure. Added an inline comment documenting
the invariant: placement inside the closure ensures every summarization attempt
(including transient-retry replays) re-checks the store.

### Low (correctness / security / documentation)

**Finding 4** — `retry-layer.ts:170-171`: `_clientToken` init relies on a
synchronous-frame invariant. Expanded the existing comment to name the exact
failure mode an `await` between client construction and `new RetryLayer()` would
cause (false-positive storeAheadOfClient on the first turn).

**Finding 5** — `provider-query-setup.credential.ts:42-47`:
`deriveCredentialFromStore` comment didn't state that `readStore()` is called
exactly once. Added a sentence clarifying the single-invocation invariant.

**Finding 6** — `keychain.ts:288-291`: `parseAccountIdentifier` fallback leaks
last 8 chars of the token into trace events (pre-existing, not introduced by
#4259). Added a TODO comment citing this issue and proposing a SHA-256
fingerprint as the correct fix.

**Finding 7** — `usage-limit-catch-up.ts:107-124`: `usage_limit_resume` vs
`credential_swap` divergence. Added a comment documenting the intentional design:
the usage-limit path fires inside a pause/resume lifecycle so the observable
event is a resume (durationMs:0), not a bare swap; consumers correlating swap
events must also watch hotSwapped:true resumes.
